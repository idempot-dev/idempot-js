# Design

## Context

- See `proposal.md` for motivation. This document covers how classification is expressed and
  enforced.
- `tests/spec/idempotency.feature` is generated by `scripts/sync-spec.sh` from
  `https://raw.githubusercontent.com/idempot-dev/website/main/docs/specs/idempotency.feature`.
  The script writes a four-line banner and then appends a fresh `curl` of upstream, so local
  edits do not survive a sync. The `tail -n +5` in the consistency job assumes that banner
  length.
- The `spec-consistency` CI job (`ci.yml:51-67`) diffs `tail -n +5` of the local file against
  upstream, so a local-only classification edit fails that job.
- That file is also published as documentation on the website, so its structure and any tags
  added to it are reader-facing.
- 49 scenarios in nine comment blocks. Cucumber runs them through `pnpm test:spec` in the
  `spec-compliance` job (`ci.yml:234-235`), outside the tap coverage gate.
- cucumber-js 12 is installed. Verified against a scratch feature: tags on a `Rule` are
  inherited by its scenarios, `--tags '@draft'` selects the class, `--tags '@section:2.6'`
  narrows to one section, and `--tags 'not @draft and not @library'` selects exactly the
  unclassified scenarios. Prefix matching on tags does not exist, which rules out a single
  `@draft:2.6` form for the totality check.

## Goals / Non-Goals

**Goals:**

- A reader of the published feature file can tell, per scenario, whether the draft requires
  the behaviour or the library chose it.
- CI can prove the split is complete and can run the draft set alone.
- Adding policy in future requires an explicit choice of class, not silence.

**Non-Goals:**

- Rewriting scenario text beyond what the classification requires. Assertions stay as they are.
- Splitting the feature into multiple files, or changing how the website publishes it.
- Re-litigating the behaviours themselves. The pass classifies; it does not fix the drift it
  exposes.

## Decisions

### Pure Rules, one class tag each, no scenario tags

Each `Rule` carries exactly one class tag and holds only scenarios of that class. Scenario-level
overrides are impossible: cucumber-js accumulates tags down the tree, so a scenario tag adds to
what it inherits instead of replacing it. Measured on the first attempt at this change, 11
scenarios inside `@draft` Rules carried their own `@library` tag and were reported as both
classes, which made `--tags @draft` select 24 scenarios instead of 13 and made the conflict
check select 11 instead of zero.

The consequence is a regrouping, not just a retagging: three `@draft` Rules first, then six
`@library` Rules by theme. About a dozen scenarios change position relative to their original
block, and no scenario body changes. A reader of the published page then gets the classification
from the headings alone, which per-scenario tags could not deliver.

Alternatives considered: untagged Rules with a class tag on all 49 scenarios (no scenario moves,
but the headings stop being truthful and the tags may not render on the site); tags alone
(invisible in the published page and in reports); `Rule` blocks alone (not selectable by
cucumber); two feature files (two published pages, two upstream URLs, a rewritten sync script,
and a duplicated `Background` for one logical artifact).

### Two tags per draft Rule, one per library Rule

Draft Rules carry `@draft` plus `@section:2.6`; library Rules carry `@library`. The class and the
section are separate tags because a colon-suffixed tag cannot be prefix-matched in a tag
expression, and the totality check needs `not @draft and not @library`.

### Totality is asserted by a script, selection by cucumber

Cucumber exits successfully when a selection is empty, so it cannot enforce completeness on its
own. `scripts/check-spec-classification.js` parses the feature file, resolves inherited tags,
and fails when a scenario resolves to no class or to both, when a scenario carries a class or
section tag of its own, when a `@draft` Rule has no `@section` tag, when a section tag names a
section that is absent from `SPEC.md`, when no `Rule` is `@draft`, or when the feature holds no
scenario at all. The last two matter because cucumber exits zero on an empty selection: without
them a file that lost its draft class would pass every gate. It prints the count per class and
per section, which is the number the published claim needs and the number that has to be
refreshed when the file changes.

The checker is covered by `scripts/check-spec-classification.test.js`, run with
`pnpm test:spec-classification-checker`. Fixtures cover each failure above, and one case pins
the counts of the shipped file, so a sync that changes them fails until the test and the prose
move together. Like the rest of `scripts/`, it sits outside the tap coverage gate.

Cucumber still does the selection: `--tags @draft` for the compliance run. The earlier decision
to do everything with tag expressions was wrong on two counts, both verified: an empty selection
exits zero, and per-scenario overrides do not exist.

### Classification is authored upstream

Rules and tags are written in `idempot-dev/website`, then `pnpm spec:sync` brings them here.
This keeps the consistency job meaningful and avoids a second source of truth. Consequence: the
upstream pull request lands first, and the sync commit here follows it.

### CI shape

Keep `pnpm test:spec` as the full run, then add, inside the existing `spec-compliance` job:

- `pnpm run test:spec:draft`, reported as the draft compliance result.
- `pnpm run check:spec-classification`, which fails on an unclassified, doubly classified or
  badly cited scenario, on an empty draft class, and prints the counts.
- `pnpm run test:spec-classification-checker`, which verifies the checker itself before it is
  trusted as a gate.

### Classification map

Final state, as applied. 13 scenarios across three draft Rules, 36 across six library Rules, 49 in
total, and the step sequence is the original one modulo scenario position.

Judgement calls worth knowing about: the concurrent 409 is cited to §2.7, which states the
status, even though the response body's `type` points at §2.6 and §2.6 also mentions the
conflict. The 422 for a reused key is cited to §2.7 for the same reason, while its body points at
§2.2. Empty-key rejection is filed as policy even though an empty field value is arguably not a
valid sf-string, because the middleware rejects it on length grounds and the draft does not
address empty values.

### Published claims

`README.md` and `docs/index.md` currently claim compliance without qualification. They become
statements of a traced count plus a pointer to the library-policy set. The count lives in one
place, updated in the same change that syncs a changed feature file; the CI summary prints the
current counts, and the checker's self-test pins them, so a count change fails CI until the
test and the prose are updated together.

## Risks / Trade-offs

- **Upstream-first sequencing** → the branch here cannot be green until the website pull request
  merges, because `spec-consistency` diffs against upstream `main`. Mitigation: land upstream
  first, then sync. If both must move together, accept a red `spec-consistency` on the branch
  and merge only after upstream is in.
- **Tag noise on the published page** → readers may see raw tags before the `Rule` heading.
  Mitigation: keep tags to two per Rule, let the `Rule` text carry the meaning, and preview the
  rendered docs page before the upstream pull request merges.
- **Regrouping changes report order** → scenario position moves for about a dozen scenarios, so
  a reader comparing before and after sees a reordered file. Mitigation: this document records
  the mapping, and the step text is unchanged, which a multiset comparison of all 266 step lines
  against the previous copy confirms.
- **Stale counts in prose** → mitigation as above: one location, updated in the sync change.
  `scripts/check-spec-classification.test.js` pins the shipped counts, so a sync that changes
  them fails CI until the test and the prose move together.
- **Classification ratified rather than reviewed** → a wrong class is worse than no class, since
  it now looks deliberate. Mitigation: the map above is reviewed before the upstream pass, and
  the pass is one commit per block so a reviewer can challenge a single block.
- **The pass exposes drift it does not fix** → several scenarios will move from a draft heading
  to `@library`, which will read as reduced compliance. That is the point, and it should be
  stated in the pull request description rather than discovered by a reader.

## Migration Plan

1. Upstream pull request in `idempot-dev/website`: `Rule` blocks, tags, corrected headings.
2. Merge upstream.
3. `pnpm spec:sync` here, committing the regenerated file with the CI steps and the claim
   wording.
4. Rollback: revert the CI steps and the synced file; classification degrades to comments and
   nothing else changes.
